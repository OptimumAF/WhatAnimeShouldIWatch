# 0033 — Public model promotion follows a verified aggregate data bundle

**Status:** M8.4 contract and invented compatibility checks, 2026-09-28. This decision authorizes synthetic and mocked development only. It does not approve a model, a source, publication, deployment, or a release workflow dispatch.

## One versioned bundle

Promote a model by creating a new immutable `data-v...` release bundle whose manifest names an already approved, separately verified aggregate-only v3 data bundle as `lastKnownGood`. Copy the prior bundle's recommendation graph, explorer graph, and identity catalog **byte-for-byte**. Add one item-only `model-mf-compact-v1` asset and a new manifest that binds its bytes, declared dataset, item IDs/titles, and coverage. The browser must rank the v3 graph and model from the same pinned bundle; a data-only bundle must continue to have no model fallback from legacy paths. A model promotion cannot regenerate, replace, or expand the data snapshot as a side effect. A changed data snapshot requires its own M8.3 review and release first.

The public model JSON may contain only its documented item IDs, titles, biases, embeddings, global mean, factor count, generated time, and optional documented provenance/count fields. Reject extra fields at the browser and manifest boundary so training-user factors, user mappings, histories, and private refit state cannot hide in a valid model asset. The old compact and legacy readers remain valid for their documented fields. The eventual model release package needs an exact allowlist for the five manifested files plus a separate model-promotion audit. No numeric training archive, user factors, raw ratings, refit rows, or full evaluation report belongs in its public assets. The current M8.3 data-only publisher remains data-only; it must never silently accept this model package.

## Evidence and approval bridge

The existing `model-promotion-v1` preflight checks a private v2 graph and demo catalog. It does not establish compatibility with the public v3 graph/identity catalog, permission to release a model, or a deployment trigger. Keep its invented tests and read-only purpose, but introduce a separate versioned promotion record for the v3 release path. That record must bind the exact base and candidate bundle IDs/manifests, unchanged data asset hashes, model bytes and numeric archive digest, frozen selection and final refit, the one-use final report's exact hash, a reviewed dataset-identity bridge from permitted raw training snapshot to the v3 graph, predeclared serving-path quality/latency/coverage gates against the best simple baseline, mapping/coverage floors, source/use decision references, and an owner decision on the exact candidate. A self-declared model `datasetSha256`, boolean quality claim, authored synthetic win, or retrain upload alone cannot satisfy those gates.

The promotion route must remain separate from periodic retraining. An approval-gated verifier should consume a pinned private candidate and committed exact-bundle approval, then pass only public allowlisted bytes into a write-permission release job. Before mutation, require source/use approvals for training, publication, and deployment as applicable, an approved immutable base release, repository immutable-release setting, and an absent target tag/release. Reverify before upload and compare remote immutable asset digests afterward. A failure must leave the prior bundle available. No current approval registry entry or provider-use approval exists.

Only after the immutable model release passes remote verification may a promotion request trigger an exact-tag Pages build through M8.5's verified installer and hosted checks. The trigger must carry the tag and manifest digest; the current `deploy-web.yml` fetches mutable `data-latest` and cannot serve as that trigger. An Actions artifact from weekly retraining is an experiment output until this entire path passes. M8.4 and M8's exit gate remain unchecked; M8.5 and M8.7 own hosted verification and practiced recovery.
