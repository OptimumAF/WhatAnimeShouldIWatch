# 0037 — Deploy only an exact approved immutable release to Pages

**Status:** M8.5 synthetic and mocked route, 2026-09-28. No source/use, owner, or deployment approval is granted by this decision. M8.5 and the M8 exit gate remain open until an approved hosted release passes the real check.

## Selection and build boundary

The data and model publication workflows may dispatch Pages only after their own immutable remote postcheck succeeds. They supply the release kind, versioned tag, manifest SHA-256, source run, artifact name, and exact data-only predecessor tag. The Pages workflow accepts only a `master` dispatch with separate publication and deployment variables; a model also requires training and model-promotion variables. Each job has only its needed permissions. Source/use records are rechecked before any release download. The checked-in approval registries remain empty, and no production job may be dispatched to test a gate.

The build downloads only named assets from the selected immutable release and, when declared, its immutable data-only predecessor. Remote metadata and asset digests must agree with the downloaded bytes. `prepare-pages-bundle.ts` rechecks the exact candidate against its committed publication or model approval, the recorded provider deployment use, dispatch identity, and previous bundle. A first data bundle needs the separately reviewed genesis approval from decision 0032; an ordinary bundle needs the exact verified predecessor. The installer activates a new clean build store atomically and retains the named predecessor. Neither `data-latest` nor the independent explorer sample can select a deployed recommendation bundle.

Offline fixture, type, unit, Python, workflow, mocked browser, and project-path preview checks run before building a candidate Pages artifact. Vite uses the actual repository base path for scripts, CSS, icons, manifest, and versioned data reads. The build verifier checks the active pointer and manifest digest, exact current/prior public inventories and hashes, absence of legacy root assets, and a matching `404.html` entry for direct navigation. Only after that gate does the narrowly permitted Pages job upload the static output.

## Hosted evidence and limits

The post-deploy read-only job probes the returned HTTPS Pages URL at the exact project path, checks direct navigation, active pointer, manifest and every declared graph/explorer/catalog/model byte hash, and requires a missing model file for a data-only release. It requests gzip for the graph, decodes and verifies it if served, and records whether gzip was observed. It reports the presence of common security headers because GitHub Pages controls their delivery; absence is visible for review rather than invented as a setting this repository can enforce. Requests, retries, and compressed/plain sizes are bounded. The hosted run must be reviewed before M8.5 can pass. A local preview and mocked HTTP tests do not establish real CDN behavior, URL handling, security headers, compression, or rollback.

Pages currently reports `build_type: workflow` for this repository. No Pages setting, repository variable, secret, release, or hosted file was changed while developing this route. The first real deployment still requires permitted source/use, exact bundle and owner review, approved repository variables, a published immutable release, owner review of the Pages run and hosted report, and M8.7 recovery practice. A data-only deployment after a model release intentionally serves no model; that replacement must be reviewed as the exact approved data bundle rather than silently borrowing an older model.
