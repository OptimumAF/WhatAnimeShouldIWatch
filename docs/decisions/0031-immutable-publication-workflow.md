**Status:** M8.3 workflow protocol, 2026-09-28. This authorizes invented-package and mocked GitHub checks only. Decisions 0001, 0002, 0028, and 0030 still hold real publication.

## Reviewed input

Both jobs require the repository's `master` ref so an unmerged branch cannot supply its own approval records or verification scripts.

The publication job accepts a dispatch with a versioned `data-v...` tag, a numeric same-repository Actions run ID, and an exact artifact name. It downloads only that named artifact from that run. The artifact is an audited five-file package from decision 0030, with no wrapper directory or extra entry. Run ID pinning alone is insufficient because Actions artifacts may be removed or replaced; a committed `docs/approvals/publication-bundles.json` entry must independently pin the tag, bundle ID, exact manifest and audit byte hashes, source run ID, artifact name, named prior tag, decision reference, publication approval reference, and owner. The initial record is empty. A maintainer must inspect the exact candidate and approve that entry in a reviewed change before the owner sets the use-specific repository variables.

The job keeps the decision-0002 publication job condition and verifies `docs/approvals/provider-data.json` immediately after checkout, before downloading the package. A local verifier recomputes the package from its four named bytes and the separately named prior bundle, compares all five bytes and audit claims, and matches the committed package approval and use-specific approval record. It rejects synthetic-only or unpublishable packages, user-linked or undeclared files, stale hashes, changed priors, missing quality evidence, and a tag/input mismatch. The prior is fetched by a distinct versioned tag with exact asset names; mutable `data-latest` is invalid. The committed approval list and prior-release bootstrap rule currently prevent a real candidate from passing.

## Remote preflight and mutation

Before any release mutation, query GitHub's immutable-release setting and require `enabled: true`; reject an existing release **or tag** at the candidate name. GitHub's setting endpoint requires repository administration **read** access, which the ordinary `GITHUB_TOKEN` cannot express. An owner must provision a separate `RELEASE_IMMUTABILITY_READ_TOKEN` secret with only that read permission; an absent or denied secret fails before download. The verification job uses `contents: read` and `actions: read`; only the dependent publication job receives `contents: write`. The workflow must use a single tag-specific concurrency group and explicit five asset paths, never a glob or `--clobber`. It creates only a new release from the checked-out commit and verifies afterwards that GitHub reports an immutable published release with exactly the five expected asset names and SHA-256 digests. A failed draft or tag creation requires an owner recovery review; do not silently overwrite or resume it. Keep source code and publication records in the current TypeScript/Python stack and test the GitHub interaction with mocked responses or static workflow checks. Do not dispatch this workflow to test it.

GitHub documents that [immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases) lock assets and tags only after publication, and [`gh release create`](https://cli.github.com/manual/gh_release_create) stages assets through a draft before publishing. [`gh run download`](https://cli.github.com/manual/gh_run_download) supports an exact run ID and artifact name. The repository setting must be enabled by an authorized owner before this route can publish; a successful `gh release create` without that setting would not meet the immutable requirement.
The [repository setting API](https://docs.github.com/en/rest/repos/repos#check-if-immutable-releases-are-enabled-for-a-repository) specifies administration read permission. A missing read credential is a hold, never evidence that immutability is enabled.
