# Repository workflow

- Read `docs/DEVELOPMENT_PLAN.md` and the latest `docs/PROGRESS.md` handoff before changing code. Inspect the actual branch, commit, local changes, and applicable instructions; the reviewed SHA in the plan is a reference only.
- Work in small, reviewable slices. Verify the relevant behavior, inspect the diff, and update the plan and progress record in the same change. Check a task only after its stated acceptance criteria pass. Preserve task IDs and log material scope or dependency changes.
- Run routine development with `fixtures/synthetic-input.json`, `npm run dev:demo`, and mocked providers. Never use real usernames, viewing histories, private ratings, salts, or credentials in fixtures, logs, screenshots, tests, or commits.
- Do not fetch or regenerate production datasets, expand collection, publish data or models, route imports through a new third party, deploy, or add paid infrastructure without the relevant authorization. Keep the existing TypeScript, Python, and Rust stacks unless evidence and an approved product decision justify a change.
- Check `docs/decisions/0001-provider-data-permissions.md` before any MAL, AniList, or Jikan dependent work. Its unresolved source/use cells are holds for collection, retained caches, training, and public artifacts; continue with synthetic fixtures and mocked providers. A working public endpoint or pseudonymous ID does not clear those holds.
- For GitHub Actions retraining, data release, and Pages deployment, follow `docs/decisions/0002-provider-workflow-gates.md`. Keep use-specific repository approval variables unset until a reviewed source/use decision and owner approval are recorded. Run the synthetic gate tests and fixture PR checks; do not dispatch production jobs to test a gate.
- The compact v1 graph's optional fourth anime-pair tuple value is co-rater support. Its weight remains the mean of two user-centered scores, a pair-preference statistic, not correlation or item similarity. [Decision 0005](docs/decisions/0005-graph-edge-semantics.md) selects support-shrunk adjusted cosine for a future recommendation neighborhood; its scorer and invented benchmark are not wired to exports or consumers. [Decision 0006](docs/decisions/0006-signed-graph-evidence.md) keeps negative/zero pair preference visible with its sign but excludes it from graph recommendations and attractive model regularization; only positive weights contribute there. [Decision 0007](docs/decisions/0007-bounded-pair-selection.md) selects pair edges from exact statistics inside separate visit/key budgets; budget exhaustion fails before export. [Decision 0008](docs/decisions/0008-seeded-per-user-selection.md) selects a capped user's ratings by recorded seed/hash and records omissions and process measurements. [Decision 0009](docs/decisions/0009-graph-v2-contract.md) versions current semantics, configuration, truncation, and dataset identity in v2 recommendation exports and separates a linked explorer sample. Keep v1 readers valid; require matching v2 graph roles and provenance; never substitute the visualization sample for ranking or training. M5 split-first evaluation remains before wiring signed similarity into runtime consumers.
- When changing graph, catalog, or model producers or loaders, update `web/src/artifacts.ts` runtime contracts and the synthetic unit/browser tests together. A present unsupported or malformed artifact should fail with its file and field identified; keep missing-file legacy fallback deliberate.
- Recommendation indexes, scoring, candidate/metadata eligibility, and explanation text live in `web/src/recommendations.ts`. Characterize current outputs with synthetic unit and browser tests before changing ranking semantics; decision 0006 settles v1 negative pair-preference use, and decision 0011 specifies M4.6's weighted rank fusion, endpoints, ties, and missing-component behavior. Keep its min–max and RRF comparison references outside the browser bundle; treat rank points as relative order, not calibrated probability. M5 still owns permitted split-first production quality evaluation.
- For score explanations, follow [decision 0012](docs/decisions/0012-score-explanations.md): retain every contributing positive graph edge but count distinct source anime IDs, divide signed model title terms by the browser vector's actual mapped-weight denominator, include global mean and candidate bias, and decompose hybrid rank points from filtered source ranks and effective weights. Keep displayed equations reconciled with an explicit rounding adjustment when needed; label provenance-free reasons qualitative and disclose the absence of calibrated uncertainty. Use invented hand-computed and escaped-title browser tests when changing this path.
- For franchise diversity, follow [decision 0013](docs/decisions/0013-franchise-diversity.md). Run the selector only after central eligibility and preserve source ranking scores/order among retained titles. Existing candidate metadata may provide anime-to-anime relations; only directed Prequel/Sequel links imply an immediate predecessor. Exact or conservative Season/Part title matches suggest grouping, never a viewing prerequisite. Missing, empty, malformed, and one-sided relation payloads cannot prove a title is safe to watch first. Keep the Allow related titles option reversible and persistent, escape relation titles in cards, and do not add provider requests or infer real-world quality from the invented diversity fixture.
- Use `createCandidateEligibilityPolicy` and `rankEligibleCandidates` for graph, model, hybrid, and fallback results. Include Only intersects the active ranking's candidates; it never inserts a title into graph or model results, and it narrows the catalog baseline when that engine is active. Explicit exclusions, all watched preferences and imported seen history, missing graph-catalog entries, and required genre/year/score checks take precedence. Check eligibility before hybrid rank assignment and again before display. Model failures or empty mapped output fall back to eligible graph results, then the labeled positive-connection catalog baseline; keep the requested mode setting and report the actual engine. Treat positive-connection catalog coverage as a labeled failure path, not popularity, quality, or personal preference. Keep metadata prefetch limits and missing-data coverage visible; M6.4 owns broader catalog completeness.
- For cold-start exploration, count retained user-anime edges in the recommendation graph as a sample-based popularity proxy; never substitute the separate explorer graph or call the count global popularity. Rank by community score only where score metadata is known. Use only explicit Liked titles for weighted, exact-genre content overlap, with the shared genres and source titles visible. Pass every exploration and sparse-history fallback through the central eligibility policy; browsing and seasonal ideas must not mutate watched or liked history. Keep normal-mode metadata checks bounded, cancellation-safe, and visibly partial; verify both offline synthetic demo and mocked normal-mode journeys without real provider calls.
- For new-user model evaluation, call the browser's preference-to-vector scorer and the same candidate eligibility path; trained-user factor metrics do not validate it. [Decision 0010](docs/decisions/0010-user-vector-evaluation.md) fixes the invented holdout and ridge comparison protocol and retains the item-embedding average for now. Keep the fold-in reference outside the web bundle. Treat the synthetic result as an engineering check; M5 still requires split-first, leakage-checked evaluation on permitted inputs before production ranking-quality claims or method promotion.
- For M5 evaluation, follow [decision 0014](docs/decisions/0014-raw-interaction-splits.md): load raw scores, reject conflicting duplicate user–anime rows, allocate immutable train/validation/test IDs before centering or fitting, and validate the manifest against the same restricted snapshot before consuming raw partitions. Do not infer viewing/rating time from fetch, provider update, import, or generation times. The present exports use a seeded per-user holdout; only a reviewed verified rating/viewing event-time mapping can support temporal evaluation. The legacy MF and LightGCN scripts still read a prebuilt full graph and do not satisfy M5.2–M5.3. Keep manifests and raw partitions out of public/release assets and use invented fixture data for routine checks.
- For M5 train-only fitting, follow [decision 0015](docs/decisions/0015-train-only-preprocessing.md): pass only validated training rows into the fitter, compute user means and popularity there, and send only their centered rows through the local TypeScript pair adapter. Keep a fixed metadata snapshot separate from ratings, with no user, score, count, or derived popularity fields. The fit-only MF route emits fit/model hashes but no holdout metric; do not treat legacy MF or LightGCN results as leakage-safe. Require a fixed-membership held-out perturbation regression before treating any new model metric as leakage-safe.
- For M5 leakage regression, follow [decision 0016](docs/decisions/0016-fixed-split-leakage-regression.md): refresh the full-snapshot manifest after a synthetic perturbation, require the same training IDs and raw training rows before comparing, and reject a stale manifest. Compare user baselines, centered rows, popularity, signed pairs/support/statistics, training arrays/hashes, and every fitted model parameter under fixed seed. A new interaction that changes training membership is a different training set, not a valid invariance comparison. The split-first route still emits no quality metric; M5.4 owns validation/test discipline.
- For M5 selection, follow [decision 0017](docs/decisions/0017-validation-test-boundary.md): declare candidate and label policies before scoring, use only validation for choices, freeze the chosen configuration and snapshot binding, and create the one-use marker before any final test scoring. Keep selection and test reports in restricted local paths. The MF and browser hybrid fixtures are engineering checks; legacy LightGCN remains outside this boundary, so do not cite its metrics as M5 evidence.
- For M5 Optuna selection, follow [decision 0019](docs/decisions/0019-split-first-optuna-selection.md): use the validated raw split, train-only fitter, and validation scorer for every predeclared trial. Keep the grid in memory with one worker and exact candidate coverage; freeze the result in the same one-use report contract. The routine `ml:search` command uses invented fixtures. Do not use the old full-graph search or its test metrics for M5 claims.
- For M5 new-user evaluation, follow [decision 0018](docs/decisions/0018-new-user-split-first-evaluation.md): keep evaluation users entirely outside train-only fitting, score their 1/3/5/10 observed prefixes with the browser preference mapper and model/eligibility functions, and report model-only ranks separately from graph/catalog fallback and warm-user factor metrics. Keep all labels on validation, fixed before scoring; do not use the fit-user test partition or invented result to tune or promote a model.
- For M5 hybrid selection, follow [decision 0020](docs/decisions/0020-hybrid-validation-boundary.md): predeclare weights and fixture hashes, score only new-user validation through the browser's graph/model/eligibility/rank-fusion/final-selector path, and freeze the selected weight. Hash the reserved invented final cohort without parsing it during selection; create a one-use marker before any final parsing or scoring. Keep its official final report unrun until later M5 baseline/reporting choices are fixed, and do not promote the synthetic weight to the product default.
- For M5 baselines and ablations, follow [decision 0021](docs/decisions/0021-fair-synthetic-baselines.md): pin the invented split/validation inputs and methods before comparing; fit counts, similarity, pairs, and every MF variant from training rows only. Rank the same centrally eligible catalog IDs for every method, filling missing signal with neutral zero and disclosing coverage. Keep v1 pair preference distinct from support-shrunk adjusted cosine; negative pairs never become attractive regularization. Compare plain, positive-weighted, unit-positive, and support-shrunk positive MF at identical hyperparameters and seed. Keep the reserved final cohort unscored and do not promote a winner from authored validation.
- For M5 broader reporting, follow [decision 0022](docs/decisions/0022-synthetic-metric-report.md): use the pinned M5.6 common-universe validation cases for Recall/NDCG@10/20, restricted-catalog coverage, fixed-genre diversity, train-count popularity bias, prefix and positive-pair support slices. Bootstrap by disjoint user, not correlated prefix, and label timed 16-case evaluator runs as local diagnostics. Report missing-positive and support-zero denominators, keep the reserved final cohort unscored, and make no production-quality claim.
- For M5 artifact parity, follow [decision 0023](docs/decisions/0023-model-artifact-parity-and-safety.md): compare the Python reference with the browser's actual item scorer and eligibility/final-list path on the hash-pinned invented model at the declared tolerance. Write numeric-only NPZ plus hash-bound JSON metadata; read with pickle disabled and reject old object arrays by default. Update model loaders/exporters, runtime model contracts, and synthetic unit/browser tests together. Do not treat the source digest in web JSON as self-verifying or use parity as ranking-quality evidence.
- For M5 experiment/refit/promotion separation, follow [decision 0024](docs/decisions/0024-experiment-refit-promotion-boundary.md): keep legacy full-graph LightGCN and Jikan content results outside release selection until they share the split-first new-user harness. Validate the frozen selection and one-use final report before a train-plus-validation refit; exclude test rows and report refit hashes/counts without copying a test metric. An experiment or retrain upload is not a promoted model. The legacy data publisher rejects model files in both its source and existing target release. The model preflight is read-only and its committed approval list is empty; it does not authorize publication. Require a compatible approved release record and preserved rollback bundle before publication; provider source/use holds remain in force.
- For M5.9 synthetic LightGCN/content experiments, follow [decision 0025](docs/decisions/0025-synthetic-experiment-adapters.md): pin both candidate algorithms and ratings-free content metadata before validation scoring, feed only validated train rows to LightGCN, and compare through M5.6's exact eligible new-user cases and browser scorer/final selector. Keep the old full-graph LightGCN result and Jikan feature cache outside selection; an invented comparison cannot promote an engine.
- For M8 release bundles, follow [decision 0026](docs/decisions/0026-immutable-release-bundle.md): bind exact artifact bytes and graph/catalog/model schemas to a versioned bundle ID, recompute v2 graph links, and validate a separate named last-known-good bundle. Treat the current mutable release fetch and browser fallback as legacy until M8.2 verifies and atomically installs a complete bundle. Synthetic checks do not clear provider-use or promotion holds.
- Browser data reads and local state use `web/src/artifact-loader.ts`, `web/src/providers.ts`, and `web/src/persistence.ts` with injected `RuntimePorts`. Use fake transport/storage/clock and seeded randomness in routine tests; keep provider scheduling changes in M2.4.
- Recommendation state and named profiles now use version 5 browser keys with explicit `seen`, `liked`, and `disliked` preferences, importance, confidence, and source. Preserve untouched `wasiw.*.v1` and `.v4` sources and exact raw backups during migration; keep unknown catalog IDs, importance, and overrides visible and round-trippable. Default manual additions to Seen. After native-scale conversion, scores at or below 4/10 are Disliked, above 4 and below 7 are Seen, and 7 or above are Liked; an unscored watch is Seen and a planned title contributes no preference. A user's manual choice wins over a later import. Test corrupt and quota-rejected storage with injected ports, and show write failures rather than claiming a profile was saved. M6.6 owns full export/import, merge preview, reset, and recovery controls.
- Async imports and metadata requests receive `AbortSignal`s and guard every delayed result before changing watched state, metadata caches, or status text. A profile or recommendation-state change cancels obsolete work; local `File.text()` reads use a generation guard. Keep loading, empty, unavailable, failed, stale, and demo statuses distinct in the UI and mocked-provider tests. M2.4 still owns provider-wide rate scheduling, timeouts, `Retry-After`, and retry budgets.
- Treat catalog, provider, profile, graph, and imported strings as untrusted at every UI sink: use `textContent` or escape HTML text/attribute values, and pass image references through `safeExternalImageUrl` before rendering. Keep synthetic markup and rejected URL regression cases; do not use a real user's history for them. Verify source usage before removing dependencies, then check the lockfile with a clean install, npm audit, and the fixture/browser gates.
- Route browser AniList/MAL/Jikan reads through the shared TypeScript `ProviderScheduler`; route TypeScript crawler calls through its single process-local scheduler and Python Jikan feature reads through `JikanRequestScheduler`. Follow [decision 0003](docs/decisions/0003-provider-request-policy.md) for source limits, `Retry-After`, timeout/cancellation, and the per-runtime boundary. Test changes with injected clocks, transport, and randomness; never make a real provider call to validate a rate policy. Decision 0001's use/collection holds still apply.
- Route crawler list pages through `collectUserSnapshot` with an anonymized ID and a mocked `MalPageFetcher` in tests. Full pages persist only as checkpoints; a validated nonempty short terminal page replaces one user's raw and normalized ratings in one transaction. Keep last complete ratings on timeout, cancellation, empty/private, malformed, or capped pages. Check `collection_status` outcomes and resume offsets, and test changed scores and removed entries before changing this path. The MAL site route has no snapshot version; do not claim time-consistent provider data or lift decision 0001's collection hold.
- Keep SQLite schema changes in the transactional `user_version` migrations and verify both the unversioned legacy and M2.5 checkpoint layouts before adding columns. Never fill unknown old source IDs or timestamps with guesses. New collection rows record source route/item ID, local `fetched_at`, a fetch run, and `normalized_field_version`; only a provider-documented adapter may supply `provider_updated_at` through `VerifiedProviderPage`. Local fetch/commit times are not viewing or rating times. Follow [decision 0004](docs/decisions/0004-collection-provenance.md), retain per-run status tests, and keep raw usernames out of SQLite and logs. Provider rights remain held by decision 0001.
- Keep imported history in `web/src/import-history.ts` separate from explicit preferences in `web/src/preferences.ts`. Persist source identity, raw status, episode progress, native score and scale, including unscored and catalog-missing items, in browser state and profiles. Seen titles exclude candidates without seeding ranking; only likes seed the current positive-only pair graph, while the existing model consumes signed like/dislike evidence. Do not treat negative v1 item-pair preference as a dislike. AniList mocks declare the user's score format; do not force a 10-point response and label it native. Preview every file and mocked username import before an explicit merge or replace; replace also clears current watched picks, so show its removal counts. Seasonal browsing must not write watched or liked history. Parse only the documented local `.txt` and bounded MAL-style `.xml` subset, reject DTDs/invalid fields, and retain old state on cancellation or storage failure. Use invented data and mocked provider responses in tests; the M2.1 provider-use hold still applies to live requests and deployment.
